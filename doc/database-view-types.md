# Database View Types

The PostgreSQL schema of hsadmin-ng contains several types of views on top of its base tables.
The suffix of a view name tells its type.
This document is a reference for backend developers:
it explains what each view type does, where it comes from, and when code or people should use it.

## Placeholders

| Placeholder | Meaning | Example |
|---|---|---|
| `T` | a qualified RBAC-managed base table | `hs_office.person` |
| `t` | its short name without schema | `person` |

## Overview

| Suffix | Name | Origin | Row filter | Writable | Main consumer |
|---|---|---|---|---|---|
| `_rv` | restricted view | generated ¹ | RBAC: only rows visible to the current or assumed subject | INSERT, UPDATE, DELETE via `instead of` triggers | application code (JPA `*RbacEntity`) |
| `_iv` | identity view | generated ¹ | none | no | RBAC internals: role names, uuid ↔ idName lookup |
| `_ev` | enhanced view | direct changeset | none | no | developers and operators who need uuids resolved for human readability |
| `_hv` | historical view | `call base.tx_create_historicization('T')` in a direct changeset | none, but a session variable selects the point in time | no | audit and time-travel queries |
| `_xv` | denormalized cross-module view | direct changeset | none | no | special application lookups |
| `_v` | plain utility view | direct changeset | none | no | statistics and the audit journal |

¹ Generated for business tables; the views on the RBAC tables themselves are hand-written, see the sections below.

## `_rv` — Restricted View

The restricted view `T_rv` is the row-level access-control layer of the RBAC system
and the default access path for application code.
Its body only returns rows for which the current or assumed subject has the `SELECT` permission,
via `rbac.queryAccessibleObjectUuidsOfSubjectIds(...)`; global admins bypass the filter.
`instead of` triggers on the view check the `UPDATE` and `DELETE` permission and write through to `T`.
Only the `INSERT` check sits on the base table itself.
See [rbac-triggers-de.md](rbac-triggers-de.md) for the full trigger and enforcement matrix.

For business tables, `T_rv` is not written by hand.
It comes out of a two-stage generation pipeline:

1. The RBAC spec of the entity (`rbac()` method in the `*RbacEntity` class, a Java internal DSL)
   is rendered by `./gradlew rbacGenerate` (`RbacSpec.main`)
   into a checked-in changelog file `...-rbac.sql`,
   marked with "generated by RbacViewPostgresGenerator, do not amend manually".
2. At migration time, the changeset `...-rbac-RESTRICTED-VIEW` in that file calls the PL/pgSQL procedure
   `rbac.generateRbacRestrictedView(...)` from `1-rbac/1058-rbac-generators.sql`,
   which creates the view and its `instead of` trigger functions.

Therefore the literal `create view t_rv` statement of a business table appears in no changelog file.

The views on the RBAC tables themselves are the exception:
`rbac.role_rv`, `rbac.grant_rv`, `rbac.subject_rv`, and `rbac.own_granted_permissions_rv`
are hand-written in `1-rbac/1055-rbac-views.sql`, together with their `instead of` triggers.

In JPA, entities named `*RbacEntity` map to `T_rv` (for example `HsOfficePersonRbacEntity` → `hs_office.person_rv`),
while `*RealEntity` classes map to the unrestricted base table `T` (for example `RealSubjectEntity` → `rbac.subject`).
Queries against `_rv` views belong into the `*RbacRepository` classes, never into a `*RealRepository`.

Examples: `hs_office.person_rv`, `hs_office.partner_rv`, `hs_booking.project_rv`, `hs_hosting.asset_rv`, `rbac.grant_rv`.

## `_iv` — Identity View

The identity view `T_iv` maps each object uuid to a human-readable identifier, the *idName*,
which is derived from the business key (for example the person's family name or a partner number).
The RBAC system needs it to build role names of the form `t#idName:ROLETYPE`
and generates the lookup functions `T_uuid_by_id_name(varchar)` and `T_id_name_by_uuid(uuid)` on top of it.

It comes out of the same generation pipeline as `T_rv`:
the generated changeset `...-rbac-IDENTITY-VIEW` calls `rbac.generateRbacIdentityViewFromProjection(...)`
or `rbac.generateRbacIdentityViewFromQuery(...)` from `1-rbac/1058-rbac-generators.sql`.
Only `rbac.global_iv` is hand-written, in `1-rbac/1080-rbac-global.sql`.

The view applies no row filter and is not mapped to any JPA entity;
it is queried by the RBAC SQL code and by other generated views.

Examples: `hs_office.person_iv`, `hs_office.partner_iv`, `rbac.global_iv`.

## `_ev` — Enhanced View

An enhanced view resolves the uuids of a table via joins into human-readable identifiers
and adds computed columns "for easier human readability",
for example `rbac.role_ev` composes the `roleIdName` as `objectTable#objectIdName:roleType`.
Enhanced views apply **no** RBAC filter and therefore show **all** rows.
They exist for developers and operators who work directly on the database — not for the API.

All enhanced views are hand-written directly in Liquibase changesets
(named `...-ENHANCED-VIEW` or `...-EV`),
and none of them has `instead of` triggers, so they are read-only.
One JPA mapping exists as a diagnostic exception:
`RawRbacGrantEntity` maps to `rbac.grant_ev`.

Examples: `rbac.role_ev`, `rbac.grant_ev`, `rbac.subject_ev` (all in `1-rbac/1055-rbac-views.sql`),
`hs_accounts.account_ev` (in `9-hs-global/950-accounts/9510-hs-accounts.sql`).

## `_hv` — Historical View

The historical view `T_hv` reconstructs the rows of `T` as they were at a past transaction or timestamp.
It belongs to the historization mechanism in `0-base/030-historization.sql`:
a trigger on `T` copies every INSERT, UPDATE, and DELETE into the append-only versions table `T_ex`,
and `T_hv` joins `T_ex` with `base.tx_context` to select the latest version at the requested point in time.

A query on `T_hv` needs exactly one of these session variables, otherwise it raises an exception:

- `hsadminng.tx_history_txid` — a transaction id, or
- `hsadminng.tx_history_timestamp` — a timestamp.

Both the versions table and the view are created by `call base.tx_create_historicization('T')`
in the changeset of the related table.
Historization is currently active for:
`hs_booking.project`, `hs_booking.item`, `hs_hosting.asset`, and `hs_accounts.account`.

Historical views are query-only for audits and are not mapped to JPA entities.

## `_xv` — Denormalized Cross-Module View

The repository does not expand the suffix `_xv`; read it as a denormalized *extra* view for one specific lookup.
There is currently a single instance: `hs_booking.debitor_xv`
in `6-hs-booking/610-booking-debitor/6100-hs-booking-debitor.sql`.
It joins `hs_office.debitor`, `hs_office.relation`, and `hs_office.partner`
and computes the `debitorNumber` from partner number and debitor-number suffix,
so that the booking module can resolve a debitor without the full RBAC join cascade.

Note that the view reads the base tables, so the view itself restricts nothing;
the inline comment declares the RBAC check of the debitor as sufficient,
thus access control must come from the calling context.
It is read-only and mapped by `HsBookingDebitorEntity`.

## `_v` And Unsuffixed Utility Views

A plain `_v` suffix marks hand-written utility views without access restriction:

- `rbac.statistics_v` and `hs_statistics_v` — row counts over the schemas.
- `base.tx_journal_v` — the audit journal `base.tx_journal` joined with `base.tx_context`.

The views in the `hs_integration` schema (for example `hs_integration.contact`, `hs_integration.subscription`)
carry no suffix at all.
They are read-only export views for external systems (Znuny, Kimai, mlmmj)
under `9-hs-global/960-integrations/`.

Despite the naming pattern, `T_ex` is **not** a view but the append-only versions *table* of the historization.

## Which View Should Code Use?

| Situation | Access path |
|---|---|
| API request on behalf of a subject | `T_rv` via a `*RbacEntity` and its `*RbacRepository` |
| internal service logic that must see all rows | base table `T` via a `*RealEntity` and its `*RealRepository` |
| resolving an idName or building a role name | `T_iv` respectively its generated lookup functions |
| manual inspection on the database console | `T_ev`, `base.tx_journal_v`, `rbac.statistics_v` |
| audit question "what was the state at time X?" | `T_hv` with one `hsadminng.tx_history_*` session variable |
