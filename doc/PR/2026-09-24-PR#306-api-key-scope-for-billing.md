# PR#306: API-Key-Scope für HSBilling NG MDA

## Relevante Links (Hostsharing-intern)

- GitEA-PR: https://dev.hostsharing.net/hostsharing/hs.hsadmin.ng/pulls/306
- Taiga-Story: https://plan.hostsharing.net/project/admin-hsadmin/us/592

## Das Problem

HSBilling NG MDA braucht lesenden Zugriff auf die abrechnungsrelevanten Stammdaten von HSAdmin NG Office:
die Liste aller Debitoren und die Liste der an einem Stichtag gültigen SEPA-Mandate.
Die bisherige Fassung kennt dafür nur den Scope `*:read`.
Ein API-Key mit `*:read` und der Global-Admin-Rolle liest aber alle Daten, etwa auch Subjects, Grants und Hosting-Assets.

Einen API-Key mit Scopes anzulegen und ihm die Global-Admin-Rolle zu granten, braucht drei Requests.
Nur für den Keycloak-Sync gibt es dafür ein Werkzeug: `tools/create-api-key-for-keycloak-sync`.

## Nicht-Ziele

- Keine Änderung der Office-Endpunkte selbst.
- Kein Scope für Booking- und Hosting-Daten.
- Kein Scope für Mitgliedschafts-Daten, der kommt in einem Folge-PR.

## Die Lösung

- Das Enum `ApiKeyScope` und die OpenAPI-Definition erhalten den Scope `hs.office:billing-mda`.
  Er erlaubt nur `GET /api/hs/office/debitors` und `GET /api/hs/office/sepamandates`, jeweils mit ihren Query-Parametern,
  sowie `GET /api/hs/office/debitors/D-{debitorNumber}`, aber bewusst nicht den Abruf eines Debitors über seine UUID.
  Debitoren und SEPA-Mandate enthalten Partner, Person, Kontakt und Bankverbindung bereits eingebettet.
  Der Name nennt das Office-Gebiet und den Nutzer: den Stammdaten-Adapter (MDA, master data adapter) des Billings.
- Die Szenarien des Billings aus PR#299 und PR#300 rufen mit diesem Scope statt mit `*:read` ab.
- Szenario-Tests reichen bisher nur UUIDs an spätere Szenarien weiter, keinen Klartext-API-Key.
  `ScenarioTest` behält darum zusätzlich Werte, die `UseCase.keep(name, value)` ablegt.
  So erhalten die Szenario-Tests zu Scenario#306.01 bis Scenario#306.14 per `@Requires` den API-Key aus Scenario#306.00.
- Das neue Werkzeug `tools/api-key-create <subject-name> <scope>...` legt das API_KEY-Subject mit den Scopes an,
  grantet ihm die Global-Admin-Rolle und gibt den API-Key aus.
  Es legt den API-Key unter dem Subject-Namen auch in `.apikeys.gpg` ab,
  damit er nicht verloren geht, auch wenn er in die Konfiguration des Billings übertragen wird;
  `--no-local-store` unterdrückt das, etwa im Smoke-Test.
  Es ersetzt `tools/create-api-key-for-keycloak-sync`, dessen Name nicht zum Schema `tools/api-key-*` passt.
  Der Keycloak-Sync-Key entsteht nun mit `tools/api-key-create hsadminng.keycloak.sync rbac.subjects:sync`.
- `tools/api-key-create` nutzt die mit `APIKEY` oder `LOGIN` in der Shell exportierten Zugangsdaten vor denen aus `.environment`.
- `tools/api-key-create` verlangt mindestens einen Scope.
  Ein API-Key ohne Scope mit Global-Admin-Rolle darf alles, dafür gibt es den Provisioning-API-Key.
- Ein neues Changeset erlaubt Bindestriche im Zugriffsteil des Scopes.
  Die bisherige Fassung des Check-Constraints `api_key_scope_scope_format` lässt dort nur Kleinbuchstaben zu.

### Anleitung: API-Key für Billing-MDA anlegen

```bash
# Voraussetzung: das Backend der Stage enthält diesen PR, also den Scope und das Changeset.

# Stage wählen: .environment bestimmt HSADMINNG_API_BASE_URL und die Zugangsdaten, hier dev.
cp .environment-dev-remote .environment
source .aliases

# als Global-Admin anmelden, etwa mit dem Provisioning-API-Key der Stage aus .apikeys.gpg,
# und prüfen, dass er gilt: die Antwort zeigt "globalAdmin": true
APIKEY hsadminng.provisioning.key
HTTP GET /api/hs/accounts/current

# legt das API_KEY-Subject mit dem Scope an, grantet die Global-Admin-Rolle
# und legt den API-Key in .apikeys.gpg ab; die Ausgabe gehört in die Konfiguration von HSBilling NG MDA
tools/api-key-create hsadminng.billing.mda hs.office:billing-mda

# Prüfen: Debitoren liefern Daten, andere Endpunkte 403 Forbidden
APIKEY hsadminng.billing.mda
HTTP GET /api/rbac/context
HTTP GET /api/hs/office/debitors
HTTP GET /api/hs/office/relations
```

## Zusätzliche Änderungen

- `tools/remote backend provision-api-key --force` ersetzt einen verlorenen Provisioning-API-Key.
  Es löscht vorher das API_KEY-Subject `hsadminng.provisioning.key` und den konfigurierten Hash,
  denn der Bootstrap ersetzt nie einen gespeicherten API-Key.
  Gegen die falsche Stage muss man vorher den Stage-Namen exakt eintippen.
  Der Smoke-Test prüft das gegen die Wegwerf-Datenbank.
- `.apikeys.gpg` gliedert die API-Keys nach Stage (`HSADMINNG_API_BASE_URL`) statt nach Keycloak-Issuer,
  denn eine Stage ohne Keycloak, etwa dev mit Fake-JWT, hat keinen passenden Issuer.
  Darum teilten sich dev und int bisher einen Abschnitt, weil beide den Vorgabe-Issuer nutzten.
  Zudem gehören hsadmin-ng-API-Keys zum Backend, nicht zu Keycloak.
  `tools/remote backend provision-api-key` legt den neuen API-Key nun ebenfalls dort ab.
- `APIKEY --list` zeigt zusätzlich die Einträge unter den bisherigen Issuer-Abschnitten.
  `APIKEY --show <name>` zeigt nur noch diesen einen API-Key statt aller, `APIKEY --stages` die Abschnitte ohne Keys.

## Release Note

released: 2026-09-25

### API-key scope for the billing system

Since 2026-09-25, the API-key endpoint-scope `hs.office:billing-mda` restricts an API-key
to `GET /api/hs/office/debitors`, `GET /api/hs/office/debitors/D-{debitorNumber}` and `GET /api/hs/office/sepamandates`.
