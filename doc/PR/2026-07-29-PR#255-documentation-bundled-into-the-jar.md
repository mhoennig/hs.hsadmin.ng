# PR#255: Documentation bundled into the jar and served at /doc/

## Related Links (Hostsharing-internal)

- Taiga-Story: --
- GitEA-PR: https://dev.hostsharing.net/hostsharing/hs.hsadmin.ng/pulls/255

## The Problem

The documentation of this project is only available to whoever can build it.
Whoever operates a deployed jar has the source of the behaviour, but not its description.

The generated parts suffer most.
The RBAC diagrams already travel inside the jar below `db/changelog`, but they lie scattered next
to their changesets, with no index and as raw Mermaid source.
The scenario-test reports exist only in `build/doc/scenarios` of whoever ran `scenarioTest`.

The REST API is a case of its own.
Swagger UI reads `/v3/api-docs`, which springdoc reconstructs from the generated controller
interfaces, and that reconstruction loses every descriptive text, because the texts live in the API
definitions and never reach an annotation:
the hand-written definitions carry 31 `summary` and 321 `description` entries and business-domain
tags, the reconstruction none of them and the controller class names.
The richer documentation was in the jar all along, but unreachable.

## Non-Goals

- No change to the generators; the corporate identity reaches their output through the shared
  stylesheet only.
- No PDFs in the jar: `generateDocumentation` stays a separate artifact, needing `xelatex`.
- No copy of legal texts; the footer links to the canonical pages of hostsharing.net.
- No publication of the `rbactest` diagrams and `test/test.yaml`, which describe test-only entities.
- No authentication in front of the documentation, it being the public repository's content.

`pr-quick-check:extra-pr-docs=22`: the news page stays empty without history, and back-filling
release notes necessarily writes into the pull-request documents of the merged PRs they describe.
The count holds against the target branch; against a branch which does not have this PR's own
document yet, that document counts as a further one.

`pr-quick-check:max-scope-score=72`: the build machinery, the three rendering tools, the page
templates, the 22 back-filled notes and the corrections which building them uncovered only make
sense together; splitting them further would leave a documentation which does not build, a news
page without history, or an API documentation with a visible defect.

## Background

The bundled documentation falls into three classes, which age differently:

- **Written by hand** — the business documents, and the API definitions as a special case:
  the controller interfaces are generated from them, thus only their descriptive texts can drift.
- **Generated from the sources** — the RBAC diagrams, from the `rbac()` entity specifications.
- **Generated by running the tests** — the scenario reports, against the running API.

A reader has to see which class a document belongs to, otherwise a hand-written document reads as
authoritative as a generated one.

## The Scenarios

### Feature: documentation available from the running application

#### Scenario#255.01: Reading the documentation without the source tree

So that whoever operates a deployment can look up how the system works.

- **Given** a jar built by `bootJarWithDocumentation`
- **When** the application runs
- **Then** `/doc/index.html` presents an overview, without authentication and without network access

#### Scenario#255.02: Reading the API documentation with its descriptions

- **Then** it resolves the `$ref`s itself and shows the summaries and descriptions
    - **and** the API as implemented stays the last entry of the selection list

##### Verified by

  — `accessToApiDefinitionsShouldBePermitted`

#### Scenario#255.03: Taking the documentation along

So that a reader can keep it without unpacking a jar.

- **Given** the overview page
- **When** the reader follows the download link
- **Then** a ZIP arrives in which every link resolves, except those needing the running application

## The Solution

The documentation is collected below `static/doc` and served at `/doc/`, which
[BaseWebSecurityConfig](../../src/main/java/net/hostsharing/hsadminng/config/BaseWebSecurityConfig.java)
permits without authentication; [DocumentationWebConfig](../../src/main/java/net/hostsharing/hsadminng/config/DocumentationWebConfig.java)
resolves `/doc/` to the overview, because Spring resolves a welcome page for the context root only.

Every `bootJar` bundles the Markdown sources, thus a plain build needs no documentation tooling.
The new `bootJarWithDocumentation` task runs `scenarioTest` first and additionally renders HTML.

### News

A pull-request document may append a `Release Note` behind a `---` line, which the build collects
into the news page, newest first.
Its `released:` line names the day of the merge, because a document is started long before that:
PR#212 was started in December and merged in March.
`tools/pr-quick-check` insists that this date is current, so that it is right at merge time.
The appendix is English even in a German document, because the page is public, and its `###`
heading becomes the headline, so that an entry does not borrow a PR title written for reviewers.

Every merged pull-request document was judged by one question: can a client of the REST API observe
this change?
22 of them can and got such an appendix; build tooling, CI, test runtime, refactorings and
migrations without a visible effect did not.

The bundle contains 4 business documents, 15 RBAC diagrams, 122 scenario reports and 6 API modules.
It grows the jar from 78 to 83 MB and is offered as a 2.1 MB ZIP at `/doc/hsadmin-ng-documentation.zip`.

### Pages

`/doc/index.html` is an overview with one card per part, because a single list of 122 scenario
reports buries everything else; each card names its origin, so that the reader sees whether the
part tracks the code.
Below the cards a single line explains the icons, and every rendered document carries the same
header, a breadcrumb, links to its neighbours, the legal footer and a back-to-top button.
A link to a target without that navigation — Swagger UI, the Redoc pages, the raw specifications —
opens in a new tab and says so through a marker with a tooltip.

The corporate identity of Hostsharing eG lives in `doc/.documentation.css` and thus also reaches
the rendered documents.
The logo travels once as `hostsharing-logo.svg` and every page references it; Pandoc would inline a
reachable image into each of them, thus the header carries a marker which the build replaces by the
reference afterwards.
`doc/.hostsharing-logo.svg` comes from the Hostsharing web site, stripped of the Adobe entities
which its DOCTYPE defined and which would break once the file is inlined into HTML.

### Rendering

[tools/markdown-to-html](../../tools/markdown-to-html) renders a Markdown file to a self-contained
page, with Mermaid and PlantUML diagrams as embedded SVG and the stylesheet inlined.
Build-time rendering is the only option covering both diagram formats, because PlantUML cannot be
rendered in a browser.
It shares the PlantUML fence normalization with `tools/markdown-to-pdf` through the new
[tools/lib/plantuml-normalize.sh](../../tools/lib/plantuml-normalize.sh).

### REST API

Swagger UI reads the hand-written definitions from `/doc/api/spec/`, where `DocumentationWebConfig`
serves the `api-definition` tree from the classpath.
It resolves the `$ref`s between those files itself, thus this part needs no build tooling and works
in every build, including `bootRun`.

[tools/openapi-to-html](../../tools/openapi-to-html) additionally renders one static Redoc page per
module below `/doc/api/`.
Each page embeds its bundled specification, because a fetch of a separate file fails under `file://`,
and loads the renderer from `redoc.standalone.js` beside it, because six inlined copies of 1.1 MB
would be wasteful.
The bundled specification stays beside each page as a single JSON file, for import into API client tools.

## Additional Changes

- Moved the chapter about the documentation build out of `README.md` into `doc/README.md`, leaving
  a short pointer behind, because it had grown to 51 lines there.
- Rewrote the cross-links between the scenario reports.
  They point at the original file names, which the URL-safe slug had broken.
- Qualified three `$ref`s in `hs-office-person-schemas.yaml` by file name, without which Swagger UI
  reports an unresolvable `HsOfficePersonType` for hs-office.
  The generated sources are unchanged by this; they differ only in the timestamp of `@Generated`.
- Gave `hs-office-data-structure.md` and `projects-booking-items-and-hosting-entities.md` a title
  heading and the business glossary a consistent "HSAdmin NG", which the index otherwise labels by
  their file name.
- Added `@redocly/cli` and `redoc` to the Jenkins agent image, which `bootJarWithDocumentation`
  needs and which no CI build runs today.
- Taught `tools/pr-quick-check` to report merge conflicts: with the base as a failure, with another
  branch on origin as a warning, comparing only branches with open work touched within 30 days.
- Switched `*.svg` in `.gitattributes` from `binary` to `text`.
  That rule comes from the initial commit of 2019 and was never revisited;
  `doc/.hostsharing-logo.svg` is the only SVG in this repository, so it only ever hid the one file
  which should be readable in a diff.
